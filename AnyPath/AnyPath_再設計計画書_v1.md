# AnyPath 再設計計画書 v1.0

作成日: 2026-07-30
対象: AnyPath（Maya用パス自動修復ツール）のUI・運用フロー刷新
参照: 現行実装（`AnyPath/` 一式、README記載のv2.1設計書準拠）

---

## 0. この計画書の位置づけ

現行のAnyPathは、実装の中身（`anypath/core/`の解決カスケードS0〜S5、構造照合スコアリング、決定論性の担保、P1「誤リンクゼロ」を守るクランプ処理）は堅牢で妥当な設計になっている。問題はそこではない。

問題は、**クリエイターがツールの存在を意識し、判断を求められ、画面を読み解かなければならない場面が多すぎる**こと。具体的には次の4点をNanoから確認した。

1. 要確認パネル（REVIEWが出た時にどれを選べばいいか迷う）
2. 自己診断画面の情報量が多すぎる（8セクション一度に表示）
3. モード（auto / report_only / off）や状態表示メニューの意味が分からない
4. **目的はあくまで「短時間ですべてのパスを正常に戻す」ことだけ。初期設定に時間がかかるなら、Maya純正のパス修復機能（File Path Editor等）の方が安定するという事実がある**

4点目が最も重要な指摘であるため、これを設計の起点に据える。この計画書は「Core（解決ロジック）はそのまま流用し、UI・設定・運用フローを全面的に作り替える」スコープで書く。Coreの改修は本計画の対象外とする。

## 1. 現状分析（何が「考えさせて」いるか）

### 1.1 概念の数が多すぎる

利用者が触れる可能性のある概念を数えると、現状は以下がある。

モード3種（auto / report_only / off）、状態表示5種（normal / review / off / error / report_only）、探索ルート（恒久・お試しの2種類）、マッピング表、アンカーフォルダ、dirmap、確信度4段階（EXACT / HIGH / REVIEW / FAILED、ただしUI上はEXACT/HIGHをまとめて「自動で直しました」と表示）、自己診断画面の8セクション（動作状態・設定読込結果・探索ルート・マッピング表・インデックス・dirmap・ログ・重複インストール）。

用語対訳表（`shell/messages.py`）やエラーメッセージ規約（3要素構成）など、「専門用語を出さない」という意図は既に実装に反映されている。それでも**画面の数と選択肢の数そのもの**が多く、対訳しても「情報量が多い」という印象は変わらない。これはメッセージの言い回しの問題ではなく、情報設計（何を、いつ、誰に見せるか）の問題。

### 1.2 「考えさせる」具体的な瞬間

- シーンを開いた直後、要確認パネルが開き、REVIEWの行ごとに候補ドロップダウンから選ばせる。候補の違いが利用者にはファイルパスの文字列比較でしかなく、どれが正しいか直感的に分からない。
- 自己診断画面を開くと、探索ルート・マッピング表・dirmap・インデックスなど、普段のクリエイター業務では意味を持たない設定項目が一覧で並ぶ。
- メニューバーの「AnyPath（確認 3件）」のような表示や「一時的に停止する(off)」「停止を解除して再開する(auto)」といった項目が、いつ・なぜ使うものか説明がない。

### 1.3 純正機能との比較という論点

Mayaには`File Path Editor`（`filePathEditor`）という、切れたファイル参照を一覧・一括修復できる純正UIが標準搭載されている。AnyPathの存在価値は「それより速く、何も操作せずに直る」ことに尽きる。セットアップに手間がかかったり、シーンを開くたびに確認画面が挟まったりするなら、純正機能を使った方が学習コストが低く枯れている分安定する、というのがNanoの指摘であり、この計画が向き合うべき核心。

**設計原則として明文化する: AnyPathは「シーンを開いたら、何も操作しなくても大半のパスが直っている」状態を最速で実現するためだけに存在する。それ以外の付加価値（詳細な診断・細かい調整）は、望まれない限り目に入ってはならない。**

## 2. 再設計の方針（3つの柱）

### 柱1: 「見せない」をデフォルトにする

全て自動で直った場合、何も表示しない（現状も実はこの設計だが、実際にはREVIEWが頻発しやすい構造照合の閾値・自己診断への誘導頻度により「見えてしまう」場面が多い）。ここを徹底し、通知・確認画面が出る頻度そのものを下げにいく。

- 自動修復が完了した場合: 何もしない（現状踏襲）。トースト通知すら出さない案を検討（詳細は4.1）。
- 要確認が発生した場合のみ、最小限の1アクションで済む画面を出す。
- 自己診断画面は「見に行かないと出てこない」場所に格納し、普段の作業導線には一切現れない。

### 柱2: 選択肢を「決定」ではなく「確認」に変える

現状の要確認パネルは「候補から選ぶ」という決定を利用者に強いる。これを「AnyPathが選んだ1件を、合っていればそのまま・違えば直す」という**確認**の形に変える。

- REVIEW行にはドロップダウンではなく、AnyPathが最有力と判断した1件を大きく表示し、「これで良い」「違う」の2択にする。
- 「違う」を選んだ時だけファイル選択ダイアログが開く（複数候補の一覧比較は行わない。比較させること自体が「考えさせる」行為）。
- これにより、REVIEW件数が多くても1行あたりの操作は最大2クリックで完結する。

### 柱3: 設定・運用の概念を統合し、隠す

- **モードは実質2つに削減**: 「自動で直す（既定）」「止める」。`report_only`（検証モード）はクリエイター向け導線から外し、必要な場合のみ自己診断の奥に残す（詳細は4.3）。
- **探索ルートの「お試し／恒久」の区別を廃止**: 常に自動的に、次回以降も使う設定として扱う。上限に達したら古いものから入れ替える（LRU）。「お試しとは何か」を説明する必要自体をなくす。
- **マッピング表・アンカーフォルダ・dirmapという言葉は画面に一切出さない**: これらは全て「フォルダの覚え直し」という1つの概念に統合してUI上表現する。
- **自己診断画面は8セクション→3セクションに圧縮**: 「今の状態」「直した場所（探す場所の一覧）」「困ったときは」。dirmapのドライラン、インデックス構築状況、重複.mod検出などは、通常表示せず「詳しく見る」を開いた場合のみ表示する2階層構成にする。

## 3. 目標体験（ゴールとなるシナリオ）

### シナリオA: 大多数のケース（自動で全部直る）

1. 別PCから来たシーンを開く。
2. 数秒後、何も起きない（バックグラウンドで解決・適用が完了している）。
3. メニューバーには変化がないか、ごく控えめな「直しました」の一瞬のトーストのみ。
4. 作業を始められる。

利用者が「AnyPathが動いた」ことを意識する必要すらないのが理想。

### シナリオB: 一部だけ確認が必要なケース

1. シーンを開く。
2. 数秒後、小さな通知が右下に出る。「テクスチャ2件だけ確認をお願いします」。
3. クリックすると、2行だけのシンプルな画面が開く。各行に「AnyPathの一番の候補」とサムネイルが大きく表示され、「これでOK」ボタンと「別のファイルを選ぶ」ボタンのみ。
4. OKを押すか別ファイルを選んで閉じる。10秒以内に終わる。

### シナリオC: 何も見つからないケース

1. 同上だが、「見つかりませんでした」の行には、ファイルを直接選ぶボタンだけを大きく置く。原因説明や技術的な理由は表示しない（ログにのみ記録）。

### シナリオD: 困ったときだけ入る「詳しく見る」

普段は絶対に開かない。開いた場合も、まず「今の状態」（正常/要確認/停止中の3値のみ）だけが見え、「もっと詳しく」をクリックした先に探索ルート一覧やログフォルダへのリンクが出る、という段階的開示にする。

## 4. 具体的な変更項目

### 4.1 通知・要確認パネル

- 「すべて推奨候補で修正」ボタンは廃止候補（もともとAnyPathが自動でやるべきことであり、ボタンとして残す時点で「本来自動でやるべきことを手動でやらせている」矛盾がある）。自動修復の閾値側で吸収する方針にする。
- 要確認パネルの候補ドロップダウンをやめ、「これでOK / 違う」の2択UIへ変更（柱2）。
- 「見つからない参照シーン」セクションは維持するが、テクスチャと同じ「これでOK/違う」または「選ぶ」ボタンのみのシンプルな行に統一する。
- サムネイルは維持（視覚的に確認できることが「考えなくて済む」ことに直結するため強化する方向）。
- レポート書き出し機能は「詳しく見る」の奥に格納し、通常の要確認画面には出さない。

### 4.2 モードと状態表示

- メニュー構成を「AnyPathを一時停止する」「AnyPathの状態を見る」の2項目のみに削減。
- `report_only`（検証モード）はメニューから排除。必要なのはAnyPath開発者側の検証時のみであり、クリエイターの日常導線に置く理由がない。環境変数か自己診断画面の奥に残す。
- メニューラベルの「(確認 3件)」表示は維持してよいが、「(検証モード)」「(エラー)」のような技術寄りの状態文言は「(確認が必要です)」のような統一トーンに寄せる。

### 4.3 探索ルート・マッピング・自己診断

- 「お試し／恒久」の区別を廃止し、常時自動保存＋上限到達時は最も使われていないものから自動で入れ替える（LRUまたは最終ヒット日時基準）。利用者に「お試しですか？恒久ですか？」を聞かない。
- 探索ルート追加のUIは、要確認パネルの「このフォルダに探しに行く」的な1ボタンに一本化し、自己診断画面側の重複導線（1.1.0で追加されたもの）は整理する。
- 自己診断画面を2階層化する。
  - 第1階層（既定表示）: 状態バッジ（正常／確認が必要／停止中）、直近に自動修復した件数、「探す場所」の一覧（フォルダのみ、件数バッジ付き）、困ったときの連絡先/ログを開くボタン。
  - 第2階層（「もっと詳しく」で展開）: 現行の設定読込結果・マッピング表・dirmapドライラン・インデックス状況・重複インストール・Gate0観測状況。既存の実装をほぼそのまま move する想定（作り直しコストを抑える）。

### 4.4 導入（インストール）体験

- ドラッグ&ドロップ後の完了メッセージは現状ほぼ妥当。「次に何をすればよいか」が1行で示されている点は維持。
- 初回起動時、いきなり自己診断や設定の概念に触れさせず、「これで自動的に直ります。何もしなくて大丈夫です」という1行メッセージのみを一度だけ出す案を追加する（初回だけのオンボーディング、2回目以降は出さない）。

### 4.5 パフォーマンス・体感速度（4点目の指摘への直接対応）

Nanoの指摘「初期設定に時間がかかるなら純正機能の方が安定する」に対しては、UIだけでなく体感速度の担保が必須。

- シーンを開いてから解決処理が終わるまでの時間を計測できるようログに残し、「重いと感じるシーン」を自己診断の「詳しく見る」で特定できるようにする（インデックス構築のタイムアウトや探索ルートの肥大化が主な原因になりうるため）。
- 探索ルート自動追加時のガード（§6.4のファイル数閾値警告）は維持しつつ、警告文言をより行動しやすい形に整理する。
- 将来的な検討事項として、Maya純正のFile Path Editorとの役割分担を明確にする一文をREADMEに追加する（「AnyPathは自動化に特化し、手動での細かい調整はFile Path Editorに任せる」という住み分けの明文化）。これは実装ではなくドキュメント上の整理。

## 5. スコープ外（今回やらないこと）

- `anypath/core/` の解決アルゴリズム自体の変更（S0〜S5カスケード、構造スコアリングの重み、確信度の閾値ロジック）。既存163件のテストが担保している範囲であり、今回のUI刷新の目的（分かりやすさ）とは独立した領域のため触らない。
- Bridge層のMaya API連携部分（コレクター・アプライヤー・リファレンス復旧・XGen検出）のロジック自体の変更。呼び出し元（Shell層・状態管理）は変わるが、中身の解決処理は流用する。
- 新機能の追加（ロールバック機能、学習履歴の活用など）。設計書側で明示的に非搭載と決められているものは踏襲する。

## 6. 進め方（フェーズ分割）

### フェーズ1: 情報設計の確定（本計画書のレビュー後、着手前に実施）
- 要確認パネルの新レイアウト（ワイヤーフレーム相当）をNanoと1画面ずつ確認する。
- モード2種への統合、探索ルートのお試し/恒久廃止について、既存の設定ファイル（machine.json / config.json）の後方互換をどう扱うか（移行スクリプトの要否）を確定する。

### フェーズ2: Shell層の作り替え
- `review_panel.py`: 2択UIへの改修。
- `diagnosis_panel.py`: 2階層構成への再構築。
- `messages.py`: 新UIに合わせた文言の見直し（3要素構成の規約自体は維持）。

### フェーズ3: Bridge層の配線変更
- `AnyPath.py` のメニュー構成・状態管理（`_state`辞書のmode値の扱い）を2モード化に合わせて修正。
- `root_manager.py` のお試し/恒久区別を廃止し、LRU方式の自動管理に置き換え。

### フェーズ4: 検証
- 既存pytestスイート（Core層は無改修のため163件はそのまま通る想定）に加え、Shell層の新規UIロジックのユニットテストを追加。
- PySide6オフスクリーンでのスモークテスト（既存と同様の手法）。
- 実機Gate0検証（README記載の通り、これは引き続き人手で実施）。

## 7. 未決事項（Nanoに確認したい点）

- 探索ルートの「お試し」概念を廃止しLRU自動管理にする案について、現行のNanoの使い方で問題ないか（複数プロジェクトを行き来する場合、意図せず古い探索ルートが消えることへの許容度）。
- 自己診断画面の「もっと詳しく」に格納する情報（設定読込結果・dirmap・重複インストール等）について、削除ではなく格納で良いか、あるいは一部は完全に削除して構わないか。
- 初回オンボーディングメッセージの要否（不要ならさらにシンプルにできる）。
