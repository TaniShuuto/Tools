# 指揮役への質問・記録(P2-b 実行制御: 待ち行列・上限・保留・引き継ぎ)

拠り所は `CONTRACT_PHASE2.md` v0.2 の P2-5 / P2-7 と作業指示書 P2-b。
ここで勝手に決めず、食い違いと実装で取った仮の扱いを記す。

## Q1. 手動の実行中拒否と、契約の「同じ TS は 1 件にまとめる」

P2-5 は手動・自動を問わず「その TS が実行中なら保留し、完了後に 1 回だけ再起動」と読む。
作業指示は、既存の `has_running_job_for_ts` と統合側の「このテクスチャセットは変換中です」を
**手動に限り従来どおり**(実行中なら拒否、`convert_now` は空文字)とし、保留は `origin="auto"` だけ、と指示している。

P2-6b の「変更を反映する」(手動扱い)が変換中に押された場合、契約どおりなら保留、指示どおりなら拒否になる。
P2-8 の保留メッセージ「変換中のため、完了後にもう一度変換します」は自動追従向けにも読める。

**今回**: 作業指示に合わせ、手動の実行中は拒否、自動だけ保留。矛盾は残っている。

## Q2. 待ち行列にいる TS への手動要求

`has_running_job_for_ts` は `_jobs`(実行中・引き継ぎ中)だけを見る。待ち行列は含めない。
そのため統合側は、順番待ちの TS に対して「変換中です」と拒否しない。
`convert_now` は既存の待ち行列項目へまとめ、優先度を手動へ上げる。

実行中の手動拒否と並ぶと、「走っているときは拒否、並んでいるときはまとめる」になる。
待ち行列も拒否すべきか確認したい。

## Q3. 待ち行列から起動できなかったときの status「を戻す」

作業指示は、起動時点でキルスイッチ・シーンを再確認し、満たさなければ捨てて status を戻す、としている。
キルスイッチは既存どおり `ORIGINAL` + `MSG_KILLSWITCH`。
シーン不一致は、完了時と同じ `ORIGINAL` + `MSG_SCENE_CHANGED` にした。

「戻す」が、順番待ちに入る直前の状態(`CONVERTED_OK` / `STALE` 等)の復元を指すなら、今は復元していない。
直前状態は status 上書き前に退避していない。

## Q4. 引き継ぎのシーン確認(開始時 vs 引き継ぎ時)

P2-7 / 作業指示は「引き継いだ時点のシーンと完了時のシーンが同じときだけ切り替える」。
`result.json` が既にある場合、引き継ぎと完了が同じ呼び出しの中で続くため、
今のシーンを両方に使うと常に一致し、指示の「シーンが違う → 切り替えない」が再現できない。

**今回**: `convert_now` が `job.json` に `scene_id` を余分なキーとして書く(ワーカーは未知キーを残す)。
引き継ぎ時、`job.json` に `scene_id` があればそれを引き継ぎ時点のシーンとして使い、
無ければ recover 時点のシーンを使う。完了時のシーンと不一致なら既存の見送り。

窓を開き直したとき、ジョブ開始時と今のシーンが違う場合に切り替えない、という実害回避にもなる。
「開始時は見ず、recover 時点と poll 完了時点だけを見る」がよければ、`job.json` の `scene_id` は使わない。

## Q5. `recover_orphaned` の完了は poll イベントに出さない

`result.json` ありの孤立ジョブは `recover_orphaned` 内で `_finish_job` 相当を行う。
戻り値は従来どおり中断した TS 名だけ。引き継いだ TS は `adopted_ts()`。
すぐ終えた TS はどちらにも出ない。attach 側がイベント無しでノードだけ切り替わる。
完了イベントも返す必要があるか。

## Q6. 上限の関数が float を返したとき

P2-2 は「型が違う値は既定値」。`int` 以外(bool 含む)は既定 2。`5` は 4 に丸め、`1` はそのまま、`0` 以下は 1。
`2.5` は int ではないので既定 2 とした。float も丸めてよいか。

## Q7. P2-5b の空振り省略は未実装

自動要求の起動直前に UV ハッシュと `source_sig` を見て省略する処理は P2-a の follow に依存する。
P2-b は `uvremap_follow.py` を import しない指示のため、入れてない。

## Q8. `revert_to_original` にキルスイッチ確認は元々無かった

作業指示は `convert_now`・`poll`・`revert_to_original` の既存の確認点で待ち行列と保留を捨てる、としている。
`revert_to_original` 自体はキルスイッチを見ていなかった。統合の無効化は先に設定を落としてから
`revert_to_original` を呼ぶ。

**今回**: `_enabled_now()` が false のときだけ待ち行列と保留を捨てる、を `revert_to_original` の先頭に足した。
原本復帰の対象や戻り値は変えていない。有効なままの revert では待ち行列を捨てない。

## Q9. 予約 ID の形

`queued:<連番>`。連番は runtime インスタンス内の整数(1 から)。
ジョブ ID(`<stamp>-<hex>`)とは別系列。窓を開き直すと連番は 1 に戻る(待ち行列はメモリだけ)。
