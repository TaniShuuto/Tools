# UV Remap core (レーン A1): 契約に関する質問と判断依頼

`uvremap_core.py` を契約どおりに実装する過程で、契約文言と食い違う、または契約が決めていない点が出た。
勝手に契約を変えず、現状の実装でどう動くかと代案をここに記す。数値の根拠は
[`PROBE_CALIBRATION.md`](PROBE_CALIBRATION.md)(`python sp_maya_livesync/tests/test_uvremap_core.py --calibrate` で再現)。

優先度: Q1 と Q2 は **契約 §3.1 の文言と実装が異なる**ため、指揮役の承認が要る。Q3 以降は契約の追加・確認事項。

---

## Q1. プローブの比較窓: 「格子固定の箱型縮小」では細部テクスチャを誤検出する(契約 §3.1 手順4)

**問題**: 手順4は「比較前に双方を `s = max(1, min(W,H)//256)` の箱型ダウンサンプルで縮小」と読める。
これを文字どおり、画像の格子に固定した `s×s` の平均画像(縮小画像)を作ってバイリニアで引くと、
**正しい変換でも細部テクスチャで fail する**。原因は変換の精度ではなく、旧画像と新画像で箱型の格子の位相が
サブテクセルずれることと、シェルの拡大縮小で窓が覆う表面の広さが変わること。

測定(`A→B`、raw、ノイズの相関長 k テクセル、`n=2000` 点・シード0、正しい変換の不合格点割合。2% を超えると fail。
`python sp_maya_livesync/tests/test_uvremap_core.py --calibrate` の最後の表。詳細は `PROBE_CALIBRATION.md`):

| 解像度 (s) | k=1 | k=2 | k=4 |
|---|---|---|---|
| 256 (1): 格子固定 → 中心窓 | 16.9% → 16.9% | 8.8% → 8.8% | 3.8% → 3.8% |
| 512 (2): 格子固定 → 中心窓 | 36.1% → 3.3% | 24.8% → 2.2% | 12.9% → 0.6% |
| 1024 (4): 格子固定 → 中心窓 | 16.7% → 0.0% | 35.8% → 0.0% | 26.9% → 0.0% |
| 2048 (8): 格子固定 → 中心窓 | 1.4% → 0.0% | 15.3% → 0.0% | 34.7% → 0.0% |

(この文書の初版は別の数値(例: 512² k=1 で 54.6% → 11.2%)を載せていたが、コミット済みのコードと校正スクリプトでは
`n=512` でも `n=2000` でも再現しなかったため、再測定した値に差し替えた。初版の数値の出所は特定できていない。
結論の向き(格子固定は 1024² でも 17〜36% で fail、中心窓は 1024² 以上で 0%)は変わらない。)

`tau` を上げて解消できるかは、格子固定での `tau` 掃引を今回の校正に含めていないため未確認(初版にあった「`tau≈0.4` が要る」は再現できていない)。
契約 §3.1 手順7「細部テクスチャ(高周波ノイズ)で偽陽性ゼロ」は、格子固定では 2048² の k=2, 4 でも満たせない(上表)。

**実装した内容**(`probe_verify(..., footprint=, match_density=)`、既定は両方とも修正版):

1. `footprint="centered"`: プローブ点を中心とする `s×s` の箱型平均(縁のテクセルは重なり面積で重み付け)。
   「箱型ダウンサンプル」を点ごとに窓の位相を揃えて評価するもので、窓の大きさ `s` は契約どおり。
2. `match_density=True`: 新旧のテクセル密度比(三角形のUV面積と解像度から求める)で旧側の窓の大きさを換算し、
   新旧の窓が同じ表面の長さを覆うようにする。シェルの拡大縮小がある変換(例: LAYOUT_B のシェル0は1.5倍)に必要。
3. 契約どおりの方式は `footprint="lattice"` で残してある(定数 `PROBE_FOOTPRINT` で既定を戻せる)。

効果: 1024²(法線は 512²)で、細部・ノイズ・シーム周辺・UDIM移動・法線のすべてで pass(fail ゼロ。不合格点割合の最悪は
sRGB ノイズの 0.37%、`tau=0.10`、`PROBE_CALIBRATION.md` 表)。検出力の比較(格子固定との差)は測っていない。
`--calibrate` の負例(故意の不具合)は、下記 Q8 の例外を除いて、7種は 40 シードすべて、残りはシード0で検出した。

**判断してほしい点**: 契約 §3.1 手順4を「点中心の箱型平均」と書き換える(推奨)か、契約文言どおりの格子固定に戻すか。
戻す場合は `PROBE_FOOTPRINT = "lattice"` の1行で済むが、**細部のあるテクスチャで正しい変換が fail し、ワーカーが
公開を止める**ことになる(テスト `test_lattice_footprint_is_available_and_documented_to_false_alarm`)。

**制約(どの方式でも残る)**:
- 解像度が低い(`s<4`、つまり 1024² 未満)と、テクセル単位の細部ノイズで窓が小さすぎて誤検出し得る。
  この場合、不合格点が1つでもあれば(pass でも)`ProbeReport.notes` に `low_resolution_probe` を付ける。ワーカーは
  この注記付きの fail を警告扱いにするか、利用者に示すとよい。512² の実測では、テクセル単位の白色ノイズ(k=1, 2)で
  不合格点割合が 3.3% / 2.2% となり fail する(上表)。
- 窓は正方形なので、非一様なスケール(縦横の伸縮)がある変換では窓の覆う領域が少しずれる。測定した範囲(LAYOUT_B のシェル別倍率)では問題なし。

## Q2. プローブ: sRGB カラーの窓平均は線形光で行う(契約に記述なし)

**問題**: 変換は sRGB を線形化して補間し再符号化する(契約 §1)。プローブが符号化値のまま窓平均を取ると、
高コントラスト部で「補間の空間(線形)」と「平均の空間(符号化)」が食い違い、正しい変換でも差が出る。
sRGB の白色ノイズ(A→B)では、`tau=0.08`・`n=2000` で不合格点が 11.1% になった(現行の `tau=0.10` でも 3.6% で fail)。

**実装した内容**: `spec.colorspace == "srgb"` かつ `kind != "normal"` のとき、窓平均を線形光で取り、再符号化した値で
`tau` と比較する(アルファは生値)。`ProbeReport.params["linear_light_average"]` に記録する。
効果: 同条件で 0.75%(`tau=0.08`)/ 0.37%(`tau=0.10`)に低下(`n=512` では 1.52% / 1.08%)。

**判断してほしい点**: 契約 §3.1 に「sRGB は線形光で平均」を一文足す。

## Q3. `tau` の既定を 0.08 → 0.10 に調整した(契約 §3.1 手順6・7の許容範囲)

Q1・Q2 を直したうえでも、sRGB の白色ノイズ(相関長2テクセル)で、既定の `n=512` では `tau=0.08` だと
40 シード中 2 回(5%)が fail になった(不合格点割合の平均 1.23%、最悪 2.09%)。これは契約の「偽陽性ゼロ」を満たさない。
`tau=0.10` では 40 シードで 0 回(最悪 1.27%、平均 0.59%)。一方、`tau=0.12` 以上では平滑テクスチャの 3% ずらしが
検出できなくなる(0.9%)ため、0.10 を採用した。法線の角度 8° と `max_bad_fraction=0.02`、`n_valid<64` は契約のまま
(法線は偽陽性が0%、検出も余裕あり)。根拠表は `PROBE_CALIBRATION.md`。

契約 §3.1 手順6の「しきい値 `tau = 0.08`」を 0.10 に更新するか、指示してほしい。定数は `PROBE_TAU`。

## Q4. シグネチャへの追加引数(後方互換)

契約のシグネチャにないキーワード引数を足した。省略時の挙動は契約どおり(または上記の調整値)。**A2(ワーカー)が渡す必要がある**:

| 関数 | 追加引数 | 理由 |
|---|---|---|
| `convert_channel` | `udim: bool \| None = None` | 非UDIM(折り返し)かどうかは job.json の `udim`。`None` なら `baseline.meta["udim"]`、それも無ければ `True` |
| `probe_verify` | `udim`, `normal_mode` | 変換と同じ値を渡さないと不一致になる。**`normal_mode="off"` で変換したら、`probe_verify` にも `"off"` を渡す**(渡さないと補正前の法線が fail になる。これは正しい動作) |
| `probe_verify` | `tau`, `max_angle_deg`, `max_bad_fraction`, `min_valid`, `footprint`, `match_density` | しきい値の上書きと較正用 |

ほかに契約外の公開物: `make_snapshot()`(配列から `Snapshot` を組み立てて指紋・ハッシュ・警告・bbox を計算する。
Maya 側 B2 が `Snapshot` を作るときの入口にできる)、`compute_flipped_topology_fingerprint()`、`find_nonmanifold_faces()`、
`find_faces_without_uv()`、例外クラス `UVRemapError` / `SnapshotError` / `TextureSetNotFound` / `ChannelFormatError` / `ConversionStopped`、
`ProbeReport.excluded` / `notes` / `params`。`meta.json` には契約のキーに加えて `warnings`(スナップショットの警告)を保存する。

## Q5. `probe_verify`: `n_valid < 64` と `n_bad/n_valid > 0.02` が同時に成り立つとき

契約は両方を別々に定めていて優先順位がない。**fail を優先**した(少数の点がすべて不一致なら、採用を止めるほうが安全)。
`n_valid == 0` は `inconclusive`。逆に `n_valid < 64` で不一致がなければ `inconclusive`(`notes` に `n_valid N < 64`)。

## Q6. 法線の限界(設計書 4.6 の再確認)

- UVヤコビアン補正は、90° 回転でパラメータ化が歪んだ面に約 1.7° の残差が出る(試作と同じ。合格基準 2° 以内)。
- `F_FLIPPED`(法線反転)の接空間法線は近似。`convert_channel` が `normals_flipped_approx` を `stats["warnings"]` に載せる。
- 補正は三角形ごとの平らなフレーム。頂点接線の補間や MikkTSpace の符号規約は扱わない(最終納品はリベース＋再ベイク)。

## Q7. 実測できていないこと

- 4096² × UDIM 4タイル × 5チャンネルの所要時間(D-5.3 の 30 秒目標)。**4096² は未測定**。
  core 単体を 2048² × UDIM 4タイル(球・`wide` レイアウト、2 コアの Linux、numpy 2.5、2026-10-16)で測った結果は次のとおり
  (`convert_channel` のみ。ファイル I/O と PNG のエンコードは含まない。`probe_verify` は n=512 で各 0.05〜0.08 秒):

  | チャンネル | convert_channel |
  |---|---|
  | BaseColor (sRGB, 3ch) | 6.97 秒 |
  | Roughness (scalar, 1ch) | 4.56 秒 |
  | Metallic (scalar, 1ch) | 4.74 秒 |
  | Normal (normal, 3ch, `uv` 補正) | 6.07 秒 |
  | Height (scalar, 1ch) | 4.63 秒 |
  | 合計(5チャンネルを逐次) | **27.0 秒**(プローブ合計 0.28 秒) |

  2048² でも 30 秒目標にほぼ余裕がない(I/O を含めれば超える可能性が高い)。毎回ラスタライズのテーブルを作る現行実装
  (契約: キャッシュは Phase 2)の時間であり、4096² は画素数が 4 倍になる。ワーカー(A2)と実機で測る。
  測定コードはリポジトリに入れていない(`test_2048_four_udim_tiles` の `Case` を使った一時スクリプト)。
- 実アセットでの確認(合成メッシュのみ)。実メッシュのトポロジー(多数のシェル、極端に細長いUV、巨大な三角形)での
  ラスタライズ速度は未測定。巨大三角形は行帯に分けて処理する実装だが、実データでの確認は B1/B2 の Phase 0 に任せる。

## Q8. 契約 §3.1 手順7の「U方向 2% のずれ」は、平滑なテクスチャでは検出できない(未解決)

**問題**: 手順7は「出力を U 方向にタイル幅の 2% 以上ずらす」不具合を `fail` とすることを求める。実測では、
**平滑な(緩やかなグラデーションの)テクスチャでは 2% のずれは検出できない**。ずらしても画素値がほとんど変わらないためで、
プローブの窓や `tau` の問題ではなく、信号側の限界である(`--calibrate` の smooth 行)。

| テクスチャ | ずれ | 最大誤差 | 不合格点割合 `tau=0.08` / `0.10` | 判定(`tau=0.10`) |
|---|---|---|---|---|
| smooth | 2% | 0.081 | 0.1% / 0.0% | pass(検出できない) |
| smooth | 3% | 0.897 | 18.7% / 5.5% | fail(`n=512`・40 シードで最小 3.77%、検出 40/40) |
| detail | 2% | 0.624 | 72.0% / 65.5% | fail(40/40) |
| noise | 2% | 0.776 | 98.0% / 96.4% | fail(40/40) |

`tau` を下げれば smooth の 2% も検出できる(`tau=0.04` で 41.6%)が、その `tau` では正しい変換の sRGB ノイズが
fail する(`tau=0.04` で最悪 6.67%、`tau=0.06` で 2.35%)。テスト `test_u_shift_on_a_smooth_texture_needs_three_percent` は、
この限界を「平滑なら 3% 以上」と明記して通している(契約より緩い要件にしてある)。

**判断してほしい点**: 手順7の対象を「細部のあるテクスチャでは 2% 以上、平滑なテクスチャでは 3% 以上」と書き換える
(推奨。平滑な信号のずれは見た目の差も小さい)か、別の検出手段(例: 平滑部では勾配も比較する)を Phase 2 で足すか。

**参考(同じ表の別の余裕)**: 領域の欠落(黒抜け)は 2% の欠落で不合格点割合が平均 3.8〜3.9%(`tau=0.10`、`n=512`・40 シード)、
最小は 2.15〜2.37% と、しきい値 2% に対する余裕が小さい。2% 未満の欠落は保証できない(`PROBE_CALIBRATION.md` (c))。
