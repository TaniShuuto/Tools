# QUESTIONS_rb_a2

RB-a2(リベース依頼の任意キー `uv_old`)で、指示書と食い違う点・仮に決めた点・実機でしか確かめられない点。
コードを変える判断はここで止めてある。`schema` は 1 のまま。Painter 側(PB-a)のコードは変えていない。

## a. 契約 R-2.4 への追記案(`uv_old`)

依頼の任意キー。`schema` は 1 のまま。キーが無い依頼はこれまでどおり有効。

| キー | 型 | 既定/必須 | 意味 |
|---|---|---|---|
| `uv_old` | object \| null | 任意 | 旧 UV セットが FBX に入っているとき `{"name": str, "index": int}`。入っていない(または不明)ときは、キーが無いか `null` |

検査規則:

- `name`: 空でない str、64 文字以下、正規表現 `^[A-Za-z_][A-Za-z0-9_]*$`。実際に FBX へ書いた UV セット名。
- `index`: int(bool は不可)、`1..7`。FBX 内の UV セット番号。
- 未知のキーは落とす。`name` / `index` 以外は残さない。
- キーが無い → 有効(結果にもキーを出さない)。明示の `null` → 有効(`"uv_old": null` を保つ)。
- 不正な値 → `bad_request`。

Maya の `build_request` は `uv_old=None` のときキー自体を出さない(`null` は書かない)。
古い Painter は不明なキーを無視する(契約 R-2.4)。

## b. 名前が規則違反のとき旧 UV 無しで送る扱い(仮)

`rebase_send` は、`uvold["applied"] is True` でも `name` が規則違反(または `None`)なら `uv_old` を渡さない。
送信は成功し、依頼は旧 UV 無しとして書く。
理由: 書き出し自体は終わっているので、依頼だけ落として候補と FBX を捨てると、送れるメッシュまで失う。
この扱いは仮。名前が規則違反になる経路は、衝突回避で `uvOld_N` を付けたとき以外は想定していない。

## c. `index` を常に 1 にする根拠と、原本が複数 UV セットのとき

`export_rebase_mesh_with_uvold` は、全シェイプの UV セットがちょうど 1 つ(`len(names0) == 1`)のときだけ `uvOld` を付ける。
よって FBX 内の並びは「原本 0 番、`uvOld` 1 番」。依頼の `index` は常に 1。
原本が複数ある場合は今は `uvOld` を付けないので、キーも出さない。
将来複数セットを許すなら、実際の番号を書き出し結果から渡し、依頼の `index` をそれに合わせる必要がある。今はしていない。

## d. `reload` 不正と `uv_old` 不正が同時のときの理由コード

`parse_request` は必須キーと型の検査のあと、`reload` の値違い(`bad_settings`)を返すより前に `uv_old` を見る。
両方不正なら理由は `bad_request`(`bad_settings` より先)。テストで固定してある。

## e. 実機でしか確かめられない点

1. FBX 内の `uvOld`(または衝突時の `uvOld_1` など)の実際の番号が 1 であること。
2. Painter が UV セットを名前と番号のどちらで引くか。両方あるときは番号で引き、名前で照合する想定(下記 f)。

## f. Painter 側(PB-a)への依頼事項(提案)

`uv_old` を読むとき:

- キーが無い、または `null` → 旧 UV 無し。
- `name` と `index` がともにあれば、`index` で UV セットを引き、`name` で照合する。
- 古い Painter はキーを知らなくてよい(無視して壊れない)。
