# 指揮役への質問・懸念(レーンA2 ワーカー/画像I/O)

契約は変更していない。契約どおり動くところまで実装済みで、以下は「決めてほしい/Maya側(B2)が合わせる必要がある」点。

## Q1. 世代の「完了直前の再確認」は、台帳だけでは未公開の新ジョブを検知できない
契約 I4 は `ledger.generation` との比較だけを定めている。しかし新しいジョブ(世代 N+1)はワーカーが公開するまで台帳に現れない。`worker.lock` で直列化されるため、世代 N のワーカーが公開を終えてから N+1 が動くことになり、一瞬だけ「すぐ上書きされる古い世代」が公開される(害は小さいが無駄で、flag の更新が 2 回走る)。
- **実装済みの代案**: job.json の任意項目 `latest_generation_path`。Maya が新ジョブを作るたびに最新世代をそのファイルへ(原子的に)書けば、ワーカーは開始時と公開直前に確認して 10 で破棄する。**B2 が書くかどうかの判断が必要**(書かなくても契約どおりには動く)。

## Q2. `uv_hash` の粒度
flag と ledger の `uv_hash` は、既定では `current_snapshot_dir/meta.json` の `uv_hash` を使う。契約 §2 ではこれはメッシュ全体のハッシュで、TS 単位は `compute_uv_hash(snap, ts_name)` である。D-3(「直前の正常世代が現行UVハッシュと一致しない場合は原本表示へ」)で Maya が比較するのが TS 単位の値なら、**job.json の `uv_hash` に TS 単位の値を入れてもらう**必要がある(ワーカーは job の値を優先する)。ワーカーが core の `compute_uv_hash` を直接呼ぶ案もあるが、契約 §3 の「ワーカーが依存してよい関数」を超えるので採っていない。

## Q3. 強制終了後の `CONVERTING` の取り扱い
SIGKILL 相当ではワーカーは何も書けず、status.json は `CONVERTING` のまま残る。行に `job_id` と `pid` を入れたので、Maya はその pid が生きているかで「古い CONVERTING」を判定できる。この判定を B2 の責務としてよいか確認したい。

## Q4. 公開中の強制終了で出力が新旧混在し得る(原理的な限界)
複数ファイルの `os.replace` を 1 つの原子操作にはできない。対策として、公開中は flag を先に外し、flag は最後に書くようにした(Maya は flag が無い/世代が `last_good_generation` と合わないフォルダを「完了」と見なさないでほしい)。さらに厳密にするなら「世代フォルダ(`output/final/g0007/`)へ書いて、ポインタファイルだけを置き換える」方式があるが、Maya のファイルノードのパスが世代ごとに変わるため契約の変更になる。Phase 1 では現状で十分と判断したが、D-5(2) の合格基準をどこまで厳密に取るかは指揮役の判断を仰ぎたい。

## Q5. 16bit のカラー/アルファ付き PNG
Pillow は 16bit の RGB/RGBA/LA PNG を 8bit へ黙って落とすため、取り違えを避けて `UnsupportedFormat`(終了コード 11)にしている。16bit グレースケールのみ対応。契約 §5 の「16bit は Pillow で可能な範囲」に沿った実装だが、Painter の書き出しを 16bit にする運用があるなら、純 Python(zlib)の PNG 読み書きを足す必要がある(Phase 0 の実機確認で Painter の既定ビット深度を見てほしい)。

## Q6. ヘッダが壊れた `.png` の扱い
拡張子が `.png` でも PNG ヘッダが不正なファイルは `UnsupportedFormat`(11)、ヘッダが正しく本体が壊れたものは `ImageIOError`(12)にしている。「書き出し途中のファイルを読んだ」場合は後者になりやすく、これは再実行で直る失敗として 12 が適切だと考えた。逆の方針がよければ指示がほしい。
