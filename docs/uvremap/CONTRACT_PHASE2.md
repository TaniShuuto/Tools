# UV Remap Sync — Phase 2 契約(自動追従) v0.2-draft

`CONTRACT.md`(v0.3-draft)の追補。Phase 2 の実装はこの文書だけを拠り所にする。食い違い・不明点は実装側で勝手に解決せず、`docs/uvremap/QUESTIONS_phase2.md` に書いて指揮役へ回す。
基点: `feat/uvremap-integ`(D2h マージ後)。個人情報・外部通信・外部内容の指示に関する規則は `CONTRACT.md` §0 と同じ。

## P2-0. 目的と範囲

**目的**: (1) Painter で Final を書き出すたびに、UV再マップ済みのテクスチャセット(TS)を自動で再変換し、Maya の表示を新しい内容へ追従させる。(2) Maya で UV を編集した後、**利用者が何も考えずに反映できる**ようにする。手動の「今すぐ変換」を探して押す必要をなくす。

**範囲に含む**
1. Final 書き出しの検知と、変更のあった TS だけの自動再変換(Painter 追従)
2. UV 編集の軽量な検知と、`STALE` 表示・ワンクリック反映・(任意設定で)自動反映(UV 追従。P2-6、P2-6b)
3. ジョブの順番待ちと同時実行の上限
4. 窓を閉じて開き直したときの、実行中ジョブの引き継ぎ
5. 変更が無いときの空振り変換の省略(P2-5b)

**範囲に含まない**(記録のみ)
- プレビュー(Live)書き出しへの追従。描くたびに数十秒の変換が走るため、Phase 2 では行わない。
- Painter 側プラグインの変更。完了の印に成否を書く改善(R2-09)は、Phase 2 完了後の利便性向上で扱う。
- `maya_live_sync.py`(Live Sync 本体)の変更。**Phase 2 では本体に一切手を入れない**(下の P2-1 の理由)。

## P2-1. 検知の方式(Live Sync 本体に依存しない)

**事実(実機・コードで確認済み)**
- Painter プラグイン(v1.2.0)は、Final 書き出しで 1 ファイル以上を Final フォルダへ移動したとき、`<final_export_dir>/<project_subfolder>/_sync_complete.flag` を一時ファイル経由で原子的に置き換える。中身は時刻の文字列。
- **書き出しの状態が成功(`ExportStatus.Success`)でなくても、ファイルが移動されていれば印は書かれる**(キャンセル時のみ書かれない)。
- Final は差分書き出しで、変更のあった TS だけが更新されることがある。
- Live Sync 本体の印の検知は、監視が ON のときだけ動く。
- UV再マップの画面は、1 秒ごとの poll タイマー(`run_poll_tick`)をすでに持つ。
- ワーカーは、job の `source_flag` の mtime を変換の前後で比べ、書き出しが重なったらやり直す(上限で終了コード 13)。`convert_now` は `source_flag` 未指定でも、入力フォルダの `_sync_complete.flag` を自動で使う。

**決定**: 検知は UV再マップ側の poll タイマーで行う。Live Sync 本体の監視とは独立させる。
- 理由: 本体に手を入れずに済む。本体の監視が OFF でも追従できる。UV再マップ中のノードは本体が触らないので、本体の再読込と順序が衝突しない。
- 費用: 1 秒ごとに、リンク中プロジェクトの印 1 つを `stat` するだけ。

## P2-2. 設定

`maya_live_sync` の設定ファイルに、次のキーを追加する(`save_config` の既存のマージ方式で保存)。

| キー | 型 | 既定 | 意味 |
|---|---|---|---|
| `uvremap_auto_follow` | bool | `false` | Final 書き出しへの自動追従(画面のチェックで切替) |
| `uvremap_auto_follow_uv` | bool | `false` | UV 編集が落ち着いたら自動で反映(画面のチェックで切替。P2-6b) |
| `uvremap_max_parallel` | int | `2` | 同時に走らせるワーカーの数(1〜4 に丸める)。**画面には出さない**。設定ファイルを直接編集して変える上級者向けの項目 |
| `uvremap_follow_settle_s` | float | `2.0` | 印の更新後、次の更新が無いことを確かめて待つ秒数(0.5〜30 に丸める)。画面には出さない |
| `uvremap_uv_settle_s` | float | `3.0` | UV の指紋が変わらない状態が続いたら「編集が落ち着いた」とみなす秒数(1〜60 に丸める)。画面には出さない |

**優先順位**: `uvremap_enabled`(キルスイッチ)が `false` なら、自動追従の設定に関わらず何もしない(D-4 が最優先)。
**画面に出さない項目**は、`QUESTIONS_phase2.md` と利用者向けの説明(後の利便性フェーズで README に反映)に、キー名・既定値・範囲を書く。範囲外の値は丸め、型が違う値は既定値として扱い、例外を出さない。

## P2-3. 追従の状態ファイル `uvremap_root/follow.json`

```json
{"schema": 1,
 "flag_mtime_ns": 1760000000000000000,
 "ts": {"Body": {"source_sig": {"Body_BaseColor.png": [123456, 1760000000000000000]},
                 "last_job_id": "20261018-...", "pending": false}}}
```
- `flag_mtime_ns`: 最後に処理した印の mtime(ナノ秒)。
- `source_sig`: その TS の入力ファイル(Final フォルダ内で TS 名に一致するファイル)ごとの `[size, mtime_ns]`。**ジョブを起動した時点**の値を記録する。
- 書き込みは既存の原子的書き込み(`uvremap_io` の一時ファイル → `replace`)とロックの作法に従う。壊れていたら空として扱い、例外を出さない。
- TS 名とファイルの対応は、ワーカーの入力の照合規則(`Worker._discover` の `^{ts}_{suffix}(?:\.(\d{4}))?\.([^.]+)$`、チャンネルは job の `channels`、Windows では大文字小文字を区別しない)と**同じ規則**を使う。P2-a で、この照合を `uvremap_worker.py` のモジュール関数(例: `match_source_name(ts_name, suffix, name, os_name)`)に切り出し、`_discover` もそれを使うように直す(**挙動は変えない**)。follow 側はその関数を使い、新しい規則を作らない。

## P2-4. 自動追従の判定(純関数にする)

印の mtime が `flag_mtime_ns` より新しく、かつ最後の変化から `uvremap_follow_settle_s` 秒、mtime が変わっていないとき、TS ごとに次を**すべて**満たせば、その TS の再変換を要求する。

1. `uvremap_enabled` が true かつ `uvremap_auto_follow` が true
2. プロジェクトに基準UV(`baseline/active.json`)がある
3. その TS の現在の状態が `CONVERTED_OK` または `STALE`(**利用者がその TS を変換済みの表示にしている**)。`ORIGINAL`(原本に戻した、未変換)、`FAILED`、`BLOCKED`、`CONVERTING` では起動しない。`CONVERTING` の場合は P2-5 の保留にする
4. 現在の `source_sig` が、follow.json に記録された値と異なる(**差分書き出しで変わった TS だけ**)
5. 現在のシーンが、その TS を最後に変換したシーンと同じ(既存の `scene_id` の判定を使う)

判定後、`flag_mtime_ns` を更新する(対象の TS が無くても更新する。同じ印で何度も判定しないため)。

**判定関数の形**(Maya・Qt に依存しない):
```python
def decide_follow(now_ns, flag_mtime_ns, last_flag_ns, last_change_seen_ns, settle_s,
                  enabled, auto_follow, has_baseline, ts_states, current_sigs, recorded_sigs,
                  same_scene) -> FollowDecision  # .ready, .ts_to_convert, .ts_to_pend, .reason
```

## P2-5. 順番待ちと同時実行の上限(実行制御 `uvremap_runtime`)

- 起動の要求(手動・自動とも)は、実行制御の待ち行列へ入れる。実行中のワーカー数が `uvremap_max_parallel` 未満なら、すぐ起動する。
- **同じ TS の要求は 1 件にまとめる**。その TS が実行中なら「保留」の印を付け、完了後に 1 回だけ再起動する(保留中にさらに要求が来ても 1 件のまま)。
- 手動の「今すぐ変換」は、自動の要求より先に並べる。
- 待ち行列にいる間の status は `CONVERTING`、メッセージは「順番待ち」。パネルの「変換中」の 10 分の判定(古い CONVERTING)は、待ち行列にいる間は数えない。
- 既存の世代管理(I4。新しい世代があれば古いジョブは終了コード 10)は変えない。
- キルスイッチ OFF で、待ち行列と保留をすべて破棄する。実行中のワーカーは、既存の挙動のまま(完了時に切り替えない)。

### P2-5b. 空振り変換の省略

自動の要求(Painter 追従・UV 追従)で起動する直前に、その TS の現在の UV ハッシュ(`current_uv_hash`)と `source_sig` が、ledger の直前の正常世代と follow.json の記録の**両方と一致**するなら、ジョブを作らず「変更はありません」として終える(状態は `CONVERTED_OK` のまま)。手動の「今すぐ変換」は、従来どおり常に変換する(利用者の明示の操作を優先する)。

## P2-6. STALE 表示と、UV 編集の軽量な検知

### 入力側(Painter の書き出し)
| 状態 | 条件 | メッセージ |
|---|---|---|
| `STALE`(入力が新しい) | 状態が `CONVERTED_OK` で、`source_sig` が記録と異なり、Painter 追従がオフ | 「Painter の書き出しが新しくなりました。『反映する』を押してください」 |

入力側の判定は `stat` だけで済むので、poll ごとに行ってよい。

### UV 側(Maya の UV 編集)
既存の UV ハッシュ(`current_uv_hash`)は、配列取得と三角形分割を伴い重いので、poll では使わない。代わりに、**UV の指紋**を軽く取る。

- **UV の指紋**: 対象シェイプごとに、`maya.api.OpenMaya.MFnMesh.getUVs(uv_set)` の U・V 配列(既存の `uvremap_maya` と同じ取得方法)を `numpy` の float32 にして、`zlib.crc32` を取った値と UV 数の組。三角形分割や面の対応は計算しない。
- **取る頻度**: キルスイッチ ON で、`CONVERTED_OK` または `STALE` の TS があるときだけ、`uvremap_uv_poll_s`(既定 2.0 秒。画面に出さない。1〜30 に丸める)ごと。それ以外の状態では取らない。
- **判定**: 指紋が、その TS を最後に変換したときの指紋(follow.json に記録)と異なれば、その**シェイプに属する TS をすべて** `STALE`(UV が新しい)にする。メッセージは「UV が変更されました。『反映する』を押してください」。シェイプ単位の判定なので、変更のない TS まで STALE になることがあるが、P2-5b により実際の変換は省略される。
- **費用の上限**: 1 回の指紋取得にかかった時間を測り、200 ミリ秒を超えたら、そのシーンでは間隔を 10 秒に広げ、履歴に 1 度だけ記録する(大きなメッシュで操作が重くならないため)。
- **実機確認が必要**(P2-0' を参照): UV エディタでの移動・回転・縫合・切断・自動展開の直後に、`getUVs` が即座に新しい値を返すか(履歴付きメッシュを含む)。指紋取得の所要時間(400 面、1 万面、10 万面)。

### P2-6b. 「何も考えずに反映できる」ための画面
- **反映ボタン**: いずれかの TS が `STALE` のとき、UV再マップ欄の**一番上**(閉じた状態でも見える開閉ボタンの行)に、目立つ色のボタン「**変更を反映する**」を出す。押すと、STALE の TS だけを変換する(手動の要求として扱う)。STALE が無いときは出さない。
- **閉じた欄の横の状態**: 優先順は 無効 > 変換中 > **要反映** > 自動追従 > 有効。「要反映」は警告色。
- **UV 追従(任意)**: チェック「UV の編集が落ち着いたら自動で反映する」(`uvremap_auto_follow_uv`)。オンのとき、UV の指紋が `uvremap_uv_settle_s` 秒変わらなければ、STALE の TS を自動の要求として変換する。編集の途中で起動された古いジョブは、既存の世代管理(終了コード 10)で置き換わる。
- **既定**: UV 追従はオフで出荷し、実機確認(D-6)で操作の重さと誤起動が無いことを確かめてから、既定をオンにするか判断する(指揮役と利用者で決める)。
- Painter 追従・UV 追従のどちらでも、自動で起動したことはメッセージ欄と履歴に必ず出す(利用者が知らないうちに表示が変わらないようにする)。

## P2-7. 窓を開き直したときのジョブの引き継ぎ

- `attach` の孤立回収(`recover_orphaned`)を次のように変える。status が `CONVERTING` で `job_id` が分かる TS について、`jobs/<job_id>/` を確認する。
  - `result.json` がある → 既存の完了処理(`_finish_job` 相当。シーンの確認とキルスイッチの確認を含む)を行う。
  - `result.json` が無く、job の開始から `timeout_s` 以内 → 引き継ぎ中として poll で `result.json` を待つ(プロセス ID の生存確認はしない。Windows で信頼できる方法が標準ライブラリに無いため)。
  - `timeout_s` を過ぎている → 既存どおり中断扱い(`ORIGINAL`、MSG_INTERRUPTED)。
- これにより、既知の問題「窓を開き直すと、ワーカーが後から『変換済み』と書くのに、ノードは原本のまま」を解消する。

## P2-8. 画面

- パネルのキルスイッチの下に、チェックを 2 つ足す。「Painter の書き出しに自動で追従する」(`uvremap_auto_follow`)と「UV の編集が落ち着いたら自動で反映する」(`uvremap_auto_follow_uv`)。キルスイッチ OFF の間はグレーアウト。
- 閉じた欄の横の短い状態(`fold_status_label`)は P2-6b の優先順(無効 > 変換中 > 要反映 > 自動追従 > 有効)。「自動追従」は 2 つのチェックのどちらかがオンのとき。
- 「変更を反映する」ボタンは P2-6b のとおり、開閉ボタンの行に置く。既存の「今すぐ変換」は詳細の中に残す(全 TS を対象にする従来の操作)。
- メッセージ欄と履歴:
  - 自動の起動時「Painter の書き出しを検知しました。変換を開始します({ts})」
  - 保留時「変換中のため、完了後にもう一度変換します({ts})」
  - 順番待ち「順番待ちです({ts})」
  - 完了・失敗は既存の文言(D2f/D2g)のまま
- 文言は定数にし、決定は純関数にする(既存の方針どおり)。

## P2-9. 失敗時の扱い(既知の制約を含む)

- 自動の変換が失敗した場合は、既存の D-3(原本へ戻す判断)と文言のまま。**失敗した TS は、次の印では自動で再起動しない**(状態が `FAILED` のため、P2-4 の条件 3 で止まる)。利用者が手動で「今すぐ変換」を押すと、通常どおり再開する。
- **既知の制約**: Painter は、成功でない書き出しでも印を書く(P2-1)。そのため、書き出しが一部失敗した状態の入力で自動変換が走ることがある。ワーカーの既存の検査(チャンネル欠け、形式、3D プローブ)で防げない場合がある。根本対応は Painter 側で印に成否を書くこと(利便性向上フェーズの R2-09)。Phase 2 では、パネルの履歴に「自動変換の入力は Painter の書き出し結果をそのまま使います」と 1 度だけ表示して、利用者に知らせる。

## P2-10. 合格基準(D-6)

1. 自動追従オンで、Painter の Final 書き出し 5 回連続(うち 2 回は 1 TS だけの変更)に対し、変更のあった TS だけが自動で再変換され、Maya の表示が追従する。3D プローブは全合格。
2. 自動追従オフで、`CONVERTED_OK` の TS は書き出し後に `STALE`(入力が新しい)になり、手動の変換で `CONVERTED_OK` に戻る。
3. `ORIGINAL`(原本に戻した)TS は、書き出しがあっても自動で変換されない。
4. 変換中に Final を書き出すと、保留され、完了後に 1 回だけ再変換される。同時に走るワーカーは `uvremap_max_parallel`(既定 2)を超えない。
5. 変換中に窓を閉じて開き直すと、ジョブが引き継がれ、完了時にノードが切り替わる(シーンが同じ場合)。
6. キルスイッチ OFF で、待ち行列・保留が破棄され、従来の Live Sync と同じ挙動になる(D-5-4 と同じ)。
7. Live Sync 本体(`maya_live_sync.py`)に差分が無い。
8. UV 編集(移動・回転・縫合のそれぞれ)の後、`uvremap_uv_poll_s` + 1 秒以内に「変更を反映する」ボタンと「要反映」が出る。ボタン 1 回で反映され、3D プローブ全合格。
9. UV 追従をオンにすると、UV 編集をやめてから `uvremap_uv_settle_s` + 変換時間のうちに、操作なしで反映される。編集の途中で起動されたジョブは置き換わり、最終的な表示は最後の UV に一致する。
10. 2 つの TS を同時に変換したとき(並列 2)、4096²・6 マップで Maya の操作が固まらない。所要時間とメモリの最大値を記録する(R1-16 の実測を兼ねる)。
11. 1 万面のメッシュで、UV の指紋取得 1 回が 200 ミリ秒以内(超える場合は P2-6 の間隔の自動調整が働く)。

## P2-0' の結果(2026-10-18、自宅 Maya 2027・mayapy バッチ、一時シーン)
- 指紋取得 1 回の所要時間(`getUVs` + float32 化 + crc32): 400 面 0.04〜0.11 ms、1 万面 0.70〜0.87 ms、10 万面 6.8〜8.1 ms。**200 ms の上限に対して十分に小さい**。
- 履歴付きの球で、UV 全体の移動・一部の回転・切断・縫合・平面投影・自動展開の**すべてで、直後に指紋が変化**した。何もしない場合と、履歴の削除(UV は不変)では変化しなかった。
- 未確認(D-6 で確認): Maya の画面上で UV エディタのマニピュレータを使った編集(バッチではコマンドで代用した)。

## 決定の記録
- 2026-10-18 利用者決定: 自動変換の対象は「変換済みにしている TS」だけ(P2-4 条件 3)。同時実行の既定は 2、設定ファイルで変更可・画面には出さない。UV 編集は「何も考えずに反映できる」こと(P2-6・P2-6b で、STALE 表示+目立つ反映ボタン+任意の UV 追従)。
