## 1. 目的とスコープ

### 1.1 目的
Painterのプロジェクトを再起動・再読込せずに、MayaでUVを変更した後もテクスチャを正しく割り当てる。ユーザーの追加操作を「Mayaでの保存」以外ゼロにすることを目標とする。

### 1.2 基本方針（ペイント用UV固定＋変換）
- Painterは「基準UV」（Painterが読み込んでいるメッシュのUV）のまま固定する。
- Mayaで変更したUVとの差は、Painterの書き出しとMaya反映の間に挟む「UV再マップ変換」で吸収する。
- 原本（PainterのFinal・Live出力）は一切変更しない。変換結果は別フォルダに出力する。
- トポロジーや形状が大きく変わる場合は、変換をやめてPainter側の再読込（リベース）へ誘導する。

### 1.3 スコープ外
- ファイルを介さないメモリ直送の同期（公式手段なし）
- UV編集操作ごとのリアルタイム反映（UV座標編集の通知手段が未確認【公式で未確認】）
- 最終納品品質の法線マップ（変換は近似。最終はリベース＋再ベイク）

## 2. 用語

| 用語 | 定義 |
|---|---|
| 基準UV（ベースライン） | Painterプロジェクトが読み込んでいるメッシュのUV。不変スナップショットとして保存し、メッシュファイルのハッシュと紐付ける |
| 現行UV | Mayaシーンの現在のUV |
| テクスチャセット（TS） | Painterのテクスチャセット＝FBX内のマテリアル名＝Mayaのシェーダー名。複数メッシュ・部分フェースにまたがり得る |
| スナップショット | TSに属する全フェースのUV・頂点位置・三角形分割・トポロジー指紋 |
| 変換テーブル | 「新UVの各テクセル → 旧UVの座標（タイル番号付き）」の対応表。UVが変わらない限り再利用 |
| 世代番号 | TSごとに単調増加する番号。古いジョブの結果を破棄するために使う |
| リベース | Painter側でメッシュを再読込し、基準UVを現行UVに更新する操作 |
| 確定（フリーズ） | 変換結果を手編集した後、そのTSを自動変換の対象から外す操作 |

## 3. 全体ワークフロー

### 3.1 基準の確立（2つの入口）
**入口A: 新規・リベース時（推奨）**
1. Mayaの「Painterへ送る」で、対象メッシュをFBXとして管理フォルダへ書き出す。同時にスナップショットを取得し、FBXのハッシュと一緒に保存する。
2. Painterでそのファイルからプロジェクトを作成、または再読込する。
3. SP側プラグインが `project.last_imported_mesh_path()`【公式】とファイルのサイズ・mtime・ハッシュを共有設定へ記録する。
4. Mayaは記録されたハッシュとスナップショットのハッシュが一致することを確認して基準を確立する（G-03）。

**入口B: 既存プロジェクト（FBXを自作で送っていない場合）**
1. SP側プラグインが記録した「Painterが最後に読み込んだメッシュのパス」を使う。
2. MayaがそのFBXを一時的な名前空間に読み込んでスナップショットを取得し、取得後に削除する。
3. メッシュファイルが既に無い・変更済みの場合は基準を作れないため、リベース（入口A）を案内する。

### 3.2 日常ループ（ユーザー操作は保存のみ）
```
[Maya] UV編集 → 保存
  └ kAfterSave: 変換ONのTSについて現行UVハッシュを計算
       ├ 前回と同じ → 何もしない
       └ 変化 → 判定（4.3）→ テーブル再構築ジョブ（世代+1）
                → 最新の原本（Final / Live）から変換 → 出力 → flag

[Painter] ペイント → Live書き出し（既存）/ 保存でFinal書き出し（既存）
  └ [Maya] 原本flag検知（既存の監視）
       → 品質判定ゲートより「前」で分岐（4.10）
       → 変換ONのTSの、ハッシュが変わったファイルだけ変換ジョブ（世代+1）

[ワーカー] ロック取得 → 原本をジョブフォルダへコピー（前後でflag mtime確認）
          → テーブル参照で変換 → 一時ファイル → os.replace → 台帳更新 → flagは最後
[Maya] 出力flag検知 → 世代確認 → fileノードを出力へ向けて再読込
```

### 3.3 例外ルート
- 変換結果を手編集したい → 6章
- トポロジーや形状が大きく変わった → リベース（8章）
- 変換を止める → TSの変換をOFF。表示状態を「Final原本」へ戻す（4.10）

## 4. 変換エンジン

### 4.1 方式F（面対応、同一トポロジー）
- 新UVで各三角形をラスタライズし、テクセル中心の重心座標を求め、同じ三角形の旧UV上の位置を同じ重心座標で求めて、旧テクスチャをバイリニアでサンプリングする。
- **三角形分割は基準スナップショットのものを両側で共有する。** 三角形は「(フェースID, フェース内コーナー番号)×3」で保存し、現行UVは `getPolygonUVid(face, corner)`【公式】で引き直す。UVの切断・縫合ではUV IDが変わるが、フェースとコーナーの対応は変わらないため正しく動く。
  - `getTriangles()` はメッシュ頂点IDを返すため【公式】、フェース内コーナー番号へ変換して保存する。同じ頂点がフェース内で重複する非多様体フェースは曖昧になるため検出して除外し、報告する。
- **Painter側の三角形分割との一致**: PainterはFBX読込時に自分で四角形を分割する。非平面の四角形では対角線がMayaと異なり、対角線付近に小さな誤差が出る【推論】。入口Aでは「三角形化して送る」（既定ON）で、Mayaの分割と同じ三角形メッシュをPainterへ渡し、誤差の原因を取り除く。
- 精度【実測】: 幾何は厳密（平滑信号で内部102.6 dB）。高周波の細部は再サンプリングでぼける（同解像度で約22 dB、元解像度を2倍にするごとに約+3 dB）。

### 4.2 方式P（位置ベース、トポロジー変化）
- 新メッシュ上の各テクセルの3D位置から、旧メッシュ上の最近接点を求め、その点の旧UVでサンプリングする。
- 候補三角形はk=16以上【実測: k=1では14%誤対応、k=16で0%】。
- 最近接距離がしきい値（バウンディングボックス対角の1%、TSごとに調整可）を超えたテクセルは「信頼度低」として集計し、割合が2%を超えたら停止してリベースを案内する（G-13）。
- 法線の向きが75°以上ずれる対応も「信頼度低」とする（薄い部品の裏面への誤投影対策）【実測で確認済みの処置】。
- 速度【実測】: 2048²で約21秒/タイル。テーブル構築時のみ。

### 4.3 方式の自動判定（メッシュ単位）
| 判定 | 条件 | 結果 |
|---|---|---|
| トポロジー指紋 | メッシュごとに、各フェースの頂点ID列（巡回の正規形）のハッシュが基準と一致 | 方式F |
| 法線反転のみ | 頂点ID列が逆順で一致 | 方式F（コーナー対応を反転して適用） |
| 形状一致度 | 不一致時、方式Pの距離集計で信頼度低 ≤ 2% | 方式P（警告表示） |
| それ以外 | — | 停止・リベース案内 |

- **TSのフェース集合の変化（マテリアル再割当）はトポロジー変化と区別する。** 指紋はメッシュ全体で取り、TSに属するフェースはマスクで別管理する。再割当だけなら方式Fのまま、新たに加わったフェースは「元テクスチャ無し」として報告する。
- 事前チェック: バウンディングボックス比較（G-04）。

### 4.4 変換テーブルとキャッシュ
- 内容: 新UVの各テクセルについて（旧タイル番号 int16、旧UV座標 float32×2、カバレッジマスク）。
- キー: `(基準ID, 現行UVハッシュ, 出力解像度, 方式)`。
- テクスチャ更新時は「テーブルを引いてサンプリングするだけ」になり、ラスタライズは毎回発生しない【推論・試作の処理内訳から】。
- 4096²の1タイルで約192 MB。npz圧縮で保存し、メモリには処理中のタイルのみ載せる。
- 掃除: 合計サイズ上限（既定2 GB）を超えたら最終使用時刻の古い順に削除。削除しても再生成できる。

### 4.5 チャンネル別の扱い（既存の書き出し設定に一致）【既存 sp_live_sync_plugin.py:1585-1608】
| ファイル | 元マップ | カラースペース | 補間 |
|---|---|---|---|
| `_BaseColor` | basecolor (RGB) | sRGB | 線形化して補間→再エンコード【実測: しないと最大47/255の差】 |
| `_Emissive` | emissive (RGB) | sRGB | 同上 |
| `_Roughness` / `_Metallic` / `_Height` | L | Raw | そのまま |
| `_Normal` | virtualMap `Normal_OpenGL` (RGB) | Raw | 補間後に正規化＋接空間補正（4.6） |

- v0.1にあったAOは書き出し設定に存在しないため削除した。

### 4.6 法線マップ
- UVヤコビアンに基づく接空間補正を既定とする【実測: 補正なし13〜22° → 補正後0.05〜1.7°】。
- 3Dフレームによる補正はより正確（約0.07°）だが、MikkTSpaceとの規約差が未検証のため既定にしない。
- `Normal_OpenGL` は高さ由来の細部とベイク済み法線を合成した仮想マップのため、変換はプレビュー品質と明示する。最終納品はリベース＋再ベイク。

### 4.7 パディングとシーム
- Painterの書き出しは `paddingAlgorithm: "infinite"`【既存】で、元テクスチャはパディング済み。これが無いとシームの精度が大きく落ちる【実測: 69 dB → 14.5 dB】。
- 出力にも16px以上のエッジ膨張（dilate）を適用する。

### 4.8 UDIMと非UDIM
- **UDIMプロジェクト**: タイル番号 = 1001 + floor(u) + 10 × floor(v)。タイル境界ちょうどのUVは三角形重心側へ1e-6寄せる【実測済みの処置】。
- **非UDIMプロジェクト**: 0〜1外のUVは小数部で折り返す（タイル扱いしない）。
- プロジェクトがUDIMかどうかはSP側プラグインが記録する（取得方法はPhase 0で確定、V7）。
- 出力ファイル名は原本と同じ規則 `$textureSet_<Suffix>(.$udim)`【既存】。新UVでタイル数が1↔複数に変わると名前の形式が変わるため、出力側は「新UVのタイル数」で命名する（4.10の書き換えと対）。

### 4.9 ビット深度とファイル形式
- 内部処理はfloat32。出力は原本と同じ形式・ビット深度にそろえる。
- 8bit PNG: Pillowで可。16bit PNG / EXR: OpenImageIOを推奨（任意依存。無い場合は8bitのみ対応と表示）。

### 4.10 Maya側の表示状態との統合【既存コードへの変更点】
- **表示状態を3値にする**: 既存の `quality_by_project`（Live/Finalの真偽）に加え、TS単位の `remap_active` を持つ。表示は「Live原本 / Final原本 / 変換（Live or Final由来）」となる。
- **管理フォルダへの追加**: `_managed_dirs()`、`detect_quality_by_project()`、`switch_texture_quality()` が `uvremap/output` を認識するよう拡張する【既存: maya_live_sync.py:3370, 3818, 3869】。
- **監視**: 出力フォルダを `fs_watcher` に追加し、出力flagで再読込する。
- **分岐位置**: 原本flag検知時の変換ジョブ投入は、`quality_for_project()` による判定ゲート（maya_live_sync.py:2652）より前に置く。表示がLiveのときでもFinal変換を進めておく。
- **fileノードの書き換え**: 既存の `switch_texture_quality` はフォルダだけを差し替えて名前を維持する（4017-4018）。変換表示ではノードごとに `fileTextureName` と `uvTilingMode`（単一=0、UDIM=3）を書き換え、AISSと同じカラースペースの保護（`ignoreColorSpaceFileRules`）を適用する【既存: AISS `_set_colorspace`】。

## 5. モジュール構成

| ファイル | 役割 | Maya依存 |
|---|---|---|
| `uvremap_core.py`（新規） | 変換エンジン。試作 `uvremap.py` を整理して移植 | なし（numpy、scipyは方式Pのみ） |
| `uvremap_worker.py`（新規） | 別プロセスのジョブ実行器 | なし |
| `uvremap_maya.py`（新規） | スナップショット、ハッシュ、判定、ジョブ投入、保存コールバック、FBX送信 | あり |
| `maya_live_sync.py`（変更） | 「UV変換」タブ、表示状態の3値化、監視・分岐の追加 | あり |
| `sp_live_sync_plugin.py`（変更） | メッシュ情報の記録（Phase 1）、リベース自動化（Phase 3） | Painter |

### 5.1 ワーカー（別プロセス）
- **理由**: Mayaのメインスレッドを止めない。クラッシュを隔離する。
- **実行環境**: Maya付属Pythonのnumpy有無は未確認【公式で未確認】。設定 `uvremap_python_exe` で選択（既定 `mayapy`）。初回に自己診断する。
- **入力のコピー**: 原本を直接開かず、ジョブフォルダへコピーしてから読む。コピーは短時間のopen/closeで行い、失敗時は再試行する。PainterのFinal書き出しは `os.replace` で上書きするため【既存: sp_live_sync_plugin.py:1355】、Windowsでは他プロセスが開いているとその上書きが失敗するおそれがある【推論】。
- **書き出し途中の検知**: コピー前後で原本フォルダの `_sync_complete.flag` のmtimeを比べ、変わっていたらやり直す。
- **排他と順序**: プロジェクト単位のロックファイル（既存と同じ `msvcrt.locking` 方式）。各ジョブは世代番号を持ち、完了時に台帳の最新世代より古ければ結果を破棄する。
- **出力**: 一時ファイル → `os.replace`。全ファイル完了後に台帳を更新し、最後に出力flagを書く。
- **寿命**: タイムアウト（既定300秒）。Maya終了時は実行中ジョブを中断し、起動時に残骸（古い `jobs/`）を掃除する（既存の `_cleanup_orphaned_staging_dirs` と同じ方針）。

### 5.2 Maya側スナップショット（uvremap_maya.py）
OpenMaya 2.0で取得する【公式】: `getUVs()`、`getAssignedUVs()`、`getPolygonUVid()`、`getVertices()`、`getPoints()`、`getPolygonTriangleVertices()`。

| 項目 | 規定 |
|---|---|
| UVセット | FBX送信時のカレントUVセット名を記録し、以後その名前で読む。名前が無ければ停止 |
| TSのフェース | シェーダー名（＝FBXマテリアル名＝PainterのTS名）から特定。`getConnectedShaders(instance)` を想定【未検証、V4】 |
| 複数メッシュ | UUID順に連結し、メッシュごとのフェースオフセットを保存（順序を決定的にする） |
| インスタンス | インスタンス0を使い、全インスタンスの割り当てが同一であることを要求（不一致は警告） |
| 頂点位置 | オブジェクト空間。スキン等のデフォーマーがある場合は中間（Orig）シェイプの位置を使う。中間シェイプは列挙から除外 |
| UV無しのフェース | （割り当て-1）除外し、件数を報告 |
| メッシュの識別 | UUID（リネームに強い）。結合・分離・再読込でUUIDが変わった場合は検出し、基準の取り直しを案内 |

### 5.3 UV変更の検知
- UV座標の編集を直接通知するコールバックは公式資料で確認できない。Python API 2.0には `addUVSetChangedCallback` 自体が無い【公式】。
- `MSceneMessage.kAfterSave`【公式】で現行UVのハッシュを計算し、前回と比較する。
- ハッシュ対象: UV配列、フェースごとのUV ID、TSフェースマスク。計算時間は要計測【推論: 数万フェースで数十ms】。

## 6. 変換結果の編集（3つの道）

| 道 | 操作 | 結果 | 実装時期 |
|---|---|---|---|
| 1 | Painter側で編集→保存 | 自動で再変換。常に原本から変換するため劣化は累積しない | Phase 1 |
| 2 | 出力を直接編集→「確定」 | そのTSを自動変換の対象外にし、出力を新しい原本として扱う | Phase 2 |
| 3 | 編集を透過レイヤーとして分離 | 再変換のたびに自動で上に重ねる | Phase 3 |

上書き防止: 出力ごとのハッシュを台帳（`ledger.json`）へ記録する。再変換時に出力が台帳と食い違えば手編集とみなし、上書きせず `<name>.edited_<日時>` へ退避して警告する（G-14）。

## 7. データ配置と設定

### 7.1 フォルダ
```
C:/SPMayaLiveSync/uvremap/<プロジェクト別サブフォルダ>/
  meshes/<送信ID>.fbx                      … 入口Aで送ったメッシュ（不変）
  baseline/<基準ID>/<TS名>.npz, .json       … 不変。新規IDで追加のみ
  tables/<キー>.npz                         … キャッシュ（LRUで掃除）
  output/live/, output/final/              … 変換結果 + 各 _sync_complete.flag
  ledger.json                               … 原本ハッシュ、出力ハッシュ、世代、確定状態、方式、統計
  jobs/<job_id>/                            … 入力コピー、ジョブ定義、結果
  worker.lock
```
- サブフォルダ名は、Maya側では `final_subfolder_by_project` から引く。`_project_subfolder_name()` はSP側にしか無い【既存】。
- 基準IDと「Painterが現在どの基準でペイントしているか」は台帳に記録する。参照されなくなった基準は手動の掃除コマンドで削除（自動削除はしない）。

### 7.2 共有設定JSONへの追加キー
| キー | 書き手 | 型 | 用途 |
|---|---|---|---|
| `uvremap_by_project` | Maya | `{project_key: {ts: {"enabled", "baseline_id", "frozen"}}}` | 変換対象と状態 |
| `painter_mesh_by_project` | SP | `{project_key: {"path", "size", "mtime", "sha1"}}` | Painterが読み込んだメッシュ（G-03用） |
| `uv_tile_workflow_by_project` | SP | `{project_key: bool}` | UDIMかどうか（4.8） |
| `uvremap_python_exe` | Maya | str | ワーカー実行環境 |
| `uvremap_normal_mode` | Maya | `"uv" / "geometry" / "off"` | 法線補正 |

- **書き込み方式**: 既存の `_merge_and_write_config` はトップレベルの浅いマージ【既存: maya_live_sync.py:939-957】。ネスト辞書はメモリ上の古いコピーから書くと相手の更新を消すため、新たに「ロック取得→ディスクから読む→該当キーを変更→書く」を1つのロック区間で行う関数を追加する。
- **キーの正規化**: 比較・検索は `_normalize_project_key_for_compare`、保存は `_for_storage`【既存】。
- **Save As対応**: SP側の `_migrate_project_key_entries` の対象（現状4辞書）【既存: sp_live_sync_plugin.py:828-848】に上記の `*_by_project` を追加する。プロジェクト別サブフォルダ名も変わるため、`uvremap/` 配下も新サブフォルダへ移すか、台帳で旧サブフォルダを参照する。
- 頻繁に変わる値（世代、統計）は共有JSONではなく台帳に置き、ロック競合を減らす。

## 8. リベース（Painter側の再読込）

### 8.1 位置付け
UVが確定した段階、または変換で吸収できない変更のときに行う。リベース後は基準UV＝現行UVとなり、変換は不要になる。

### 8.2 手順（Phase 3で自動化、それまでは手順を案内）
1. **Maya**: 入口Aと同じく「Painterへ送る」。FBXとスナップショットを同時に作る。このスナップショットが新しい基準になる。
   - FBXオプション【公式】: `FBXExport -f <path> -s`、`FBXExportInputConnections -v false`、三角形化は4.1の方針に従う。一時ファイル → `os.replace`。
2. **Painter**: busyでないことを確認（`is_busy` / `execute_when_not_busy`）【公式】。既存の書き出し中状態も確認する。
3. **Painter**: `save_as_copy` でバックアップ【公式】。
4. **Painter**: `reload_mesh(path, MeshReloadingSettings(preserve_strokes=True, import_cameras=False), cb)`【公式】。
   - 12.0.0には `auto_unwrap_settings` が無いと推定される（APIの版の空白からの推論）。プロジェクトや環境設定の自動展開が適用される可能性がある。`hasattr` で分岐し、12.0.2以降では自動展開を明示的に無効化する（G-07）。
5. **成功時**: SP側がメッシュ情報を記録する。続けて全量のFinal書き出し（既存の `force_full_final_sync`）を行う。その完了flagを待ってから、Maya側で基準を切り替え、TSの変換をOFFにし、表示を原本へ戻す。flagより前に戻すと、まだ旧UVのFinalが表示されてしまう。
6. **成功時の注意**: `preserve_strokes` が再投影するのはストロークのみ。ベイク済みメッシュマップ、UV投影のフィル、2Dビューのストロークは再ベイク・再確認が必要と案内する【公式】。
7. **失敗時**: バックアップの場所を案内し、変換モードを維持する。

## 14. 既知の限界とリスク
1. **細部のぼけ**: 再サンプリングは原理的に高周波を失う（同解像度で約22 dB）。対策は元解像度を上げるか、UV確定後にリベースすること。
2. **法線は近似**: 最終納品はリベース＋再ベイク。
3. **新しく増えた面にはテクスチャが無い**: 方式Pやマテリアル再割当で発生。
4. **Painter上では現行UVのテクスチャを確認できない**: Painterは基準UVのまま。確認はMaya上で行う。
5. **12.0.0固有の不確定要素**: 自動展開の挙動、APIの版数（Phase 0で確定）。
6. **numpyの実行環境**: 学校PCで入らない場合、別のPython 3を用意する必要がある。
7. **既存コードへの変更範囲が広い**: 表示状態の3値化は品質切替の中核に触れる。既存テストの回帰確認を必須とする。

## 15. 付記：既存コードで気付いた点（本機能と独立）
- `udim_setup.py` が設定パスを直書きし、環境変数 `SPMAYA_CONFIG_DIR` を無視している（L875付近）。
- 設定ロック・マージ処理がMaya側とSP側で重複実装になっている。
- Final書き出しでは `texture_set_export_prefix` を記録していない（Previewのみ）【既存: sp_live_sync_plugin.py:1373】。
- `texture_set_shading_engine_map_by_project` は `create_shader_network` で作ったネットワークにしか記録されず、AISSや `udim_setup` で作ったマテリアルは対象外。本機能はシェーダー名からTSを特定するため影響しない。
